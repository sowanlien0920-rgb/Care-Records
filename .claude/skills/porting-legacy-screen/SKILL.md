# porting-legacy-screen

単一HTML実装の1画面を React + TypeScript へ移植する。

このスキルの価値は、**移植を「作り直し」にしないこと**にある。移植中に構造を良くしたくなるが、それをやると legacy との突き合わせができなくなり、4,457行のどこを取りこぼしたのかが永久に分からなくなる。改善は移植が終わってからにする。

## 自律性レベル: Medium

コードを新規作成する。ただし**移植の範囲を勝手に広げない。** 1回の実行で扱うのは1画面ぶんとする。

## 鉄則

移植中に守るもの。破ると突き合わせが成立しなくなる。

1. **CSS を書き換えない。** `src/styles.css` は legacy の731行をそのまま持ち込んだもの。効かないときは DOM 側を legacy に合わせる
2. **クラス名を変えない。** Tailwind に置き換えない。BEM 等に整えない
3. **DOM の入れ子を変えない。** コンポーネント境界で分割してよいが、出力される HTML の階層は legacy と同一にする
4. **文言を変えない。** ラベル、ボタン名、メッセージの文字列をそのまま写す
5. **ロジックの仕様を変えない。** バグに見えるものがあっても直さない。計画書の `## 5` の「実装中に気づいた点」に記録して先に進む
6. **範囲を広げない。** 依頼された画面だけを扱う

## 手順

### 1. 計画書を読む

`docs/plans/2026-09-10-carerecords-react-migration.md` の以下を確認する。

- `## 2` の確定事項 — とくに「移植しない」と決まっているもの
- `## 4` の実装順序 — いま何ステップ目か、完了条件は何か
- `## 4` の変更対象ファイル — 作るファイル名が決まっている

**移植しないと決まっているもの**（誤って移植しないこと）。

- バックアップ機能（JSON 書き出し・復元）
- 職員アカウント管理 373行（Phase 1a では簡易ログインに置換）
- 利用者マスタのうち**法定文書に属する情報の編集機能**（kpi-react が正。carerecords では閲覧のみ）

### 2. legacy-reader に元の実装を読ませる

`legacy-reader` エージェントに、対象画面の実装を報告させる。**自分で `legacy/index.html` を読み込まない。** 4,457行を本体の文脈に載せると、以降の作業余地がなくなる。

報告に含まれる「移植時に問題になる箇所」を先に確認する。とくに入れ子依存の CSS セレクタは、DOM 階層を写す判断の根拠になる。

### 3. 画面キャプチャを確認する

`画面キャプチャ/` に該当画面のスクリーンショットがあれば見る。CSS だけでは分からないレイアウトの意図が読み取れる。

### 4. コンポーネントに分ける

分割は**コンポーネント境界のみ**で行い、DOM の階層は変えない。

```
悪い例: <div class="panel"> を消して <Panel> の中身を直接置く
良い例: <Panel> が <div class="panel"> をそのまま出力する
```

分割の粒度は計画書の変更対象ファイル一覧に従う。そこに無いコンポーネントを勝手に作らない。

### 5. 差し込み口を空で用意する

Phase 1b で入るドメインロジック（記載チェック、特記事項の自動生成、集計）は、Phase 1a では**props の受け口だけ作って空にしておく**。

```tsx
// Phase 1a ではこう
type Props = { findings?: Finding[] }   // 記載チェックの結果。Phase 1b で埋まる
```

後から差し込めるようにしておかないと、Phase 1b でコンポーネントを作り直すことになる。

### 6. データはアダプタ経由でのみ触る

`localStorage` を直接読み書きしない。必ず `useCareStore()` を経由する。Phase 5 で Firestore に差し替えるとき、ここを守っていないと差し替えが成立しない。

アダプタは `Promise` を返すため、**loading / error / empty / success の4状態を必ず扱う**（`handling-async-states` を併読する）。

### 7. parity-checker で突き合わせる

移植が終わったら `parity-checker` エージェントに、legacy と移植先の差分を報告させる。

「差分あり」「未実装」が出たら、鉄則に照らして判断する。

- 意図せず変えてしまった → 直す
- 計画で除外されている → そのまま。計画書に既に記録がある
- legacy のバグに見える → 直さない。計画書の `## 5` に記録する

### 8. 計画書を更新する

`## 5. Implementation Status` の該当ステップにチェックを入れ、以下を記録する。

- 計画から外れた点（あれば）
- 実装中に気づいた点 — **legacy のバグに見えたもの、移植を保留したもの**

## 併読する Craft Skills

計画書の `## 4` で判定済み。移植する画面に応じて読む。

| 画面の性質 | 併読 |
|---|---|
| 新しい画面・レイアウトを作る | `designing-ui-components` |
| モーダル、フォーカス管理、カスタム select、ボタン群 | `making-accessible` |
| 入力・送信を含む | `writing-forms` |
| アダプタからデータを取る（=ほぼ全て） | `handling-async-states` |

## やってはいけないこと

- **自分で `legacy/index.html` を全部読まない。** `legacy-reader` に委譲する
- **移植のついでに設計を良くしない**
- **CSS を書き換えない。クラス名を変えない**
- **legacy のバグを直さない。** 記録して先に進む
- **`localStorage` を直接触らない**
- **1回で複数画面を移植しない**
